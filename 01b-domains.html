Do you swap the tokenizer
for a new domain? And how is one built?

Both come down to one fact: a tokenizer is learned from a corpus — it's tuned to whatever text it was trained on. So it's efficient on that, wasteful off it. Real runs below.

1 · Do you change it?

The "tokenizer tax."

GPT-2's tokenizer is byte-level, so it can encode anything — any language, code, DNA — it never fails. But it was trained on English web text, so off-domain input is wildly inefficient: the same greeting costs far more tokens. More tokens = more money + less usable context. Same sentence "Hello, how are you today?", ten domains:

English7 tokHello, how are you today?
Python code11 tokdef add(a, b): return a + b
German12 tokHallo, wie geht es dir heute?
Spanish13 tokHola, ¿cómo estás hoy?
DNA14 tokATCGGCTAGCTAGCTAGCATCGATCG
Chinese21 tok你好，你今天怎么样？
Japanese21 tokこんにちは、今日はどうですか？
Arabic24 tokمرحبا، كيف حالك اليوم؟
Russian27 tokПривет, как дела сегодня?
Hindi36 tokनमस्ते, आज आप कैसे हैं?

Same meaning: 7 tokens in English → 36 tokens in Hindi. That ~5× gap is a real cost non-English users pay.

So — three choices

Reuse it (default): fine if your text is close to the original. Byte-level means it never breaks, just gets pricey off-domain.

Train a new one: if your domain is far (code, Hindi, protein/DNA, legal), train fresh BPE on your corpus → far fewer tokens per input. StarCoder, multilingual models, BloombergGPT all do this.

Extend it: bolt domain tokens onto a pretrained tokenizer + continue training — the cheap way to adapt an English model to a new language.

2 · How is one built?

Byte-Pair Encoding, built by hand.

The whole training algorithm:
1. start with the raw alphabet (characters / bytes)
2. count every adjacent pair in the corpus
3. merge the most frequent pair into one new token; add it to the vocabulary
4. repeat until you hit your target vocab size

The learned merge rules, in order, are the tokenizer. Here's that loop run for real — the first 8 merges it discovers, trained separately on English prose vs Python code. Watch the units it invents:

trained on prose

1·+t→·t×107
2h+e→he×66
3·t+he→·the×65
4·the+·→·the·×47
5r+e→re×36
6m+o→mo×30
7e+c→ec×30
8·t+o→·to×30

trained on code

1·+·→··×90
2\n+··→\n··×30
3\n··+··→\n····×30
4·+a→·a×24
5,+·→,·×24
6d+e→de×18
7de+f→def×18
8)+:→):×18

Same algorithm, opposite vocabulary

Prose builds toward words — watch ·the assemble itself merge by merge (·+t → ·t, then +he → ·the). Code's very first merge is two spaces (indentation!), then a newline+indent, then def and ): emerge as single tokens. A prose tokenizer would never spend vocab on indentation; a code tokenizer must. That's why domain tokenizers exist.

The aha

A tokenizer isn't fixed machinery — it's a compression scheme learned from a pile of text. Point it at different text and it invents different units. Change the domain far enough and you retrain it.

Build a real one with: HuggingFace tokenizers (fast BPE), Google sentencepiece (Llama/T5), or Karpathy's minbpe (the ~read-it-all educational version). Raschka ch02 builds a simple one too.
