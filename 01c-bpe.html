What BPE really is — and how it trains, behind the scenes.

Past "what it does" to the actual machinery inside .train() — the real internal tables, iteration by iteration — plus a tokenizer trained from scratch and why off-domain text is expensive. Every number is a real run.

1 · What the name means

A compression algorithm, applied to bytes.

Byte-Pair Encoding was invented in 1994 to shrink files: repeatedly find the most common pair of adjacent bytes, replace it with one new symbol, repeat. "Encoding" = compression. LLMs reuse that exact trick, and the merge table becomes the vocabulary.

Why "byte"

Modern tokenizers start from the 256 possible byte values, not letters. Text → UTF-8 bytes → BPE on bytes. That's why nothing is ever "unknown" — every byte is already in the vocabulary.

2 · Behind the scenes — what .train() actually does

It's just: count pairs → merge the top one → rewrite. Deterministic.

No gradients, no loss, no learning rate. Here is the trainer's real internal state on the corpus "the cat sat on the mat the cat naps the cat".

First pass, count unique words. From now on the trainer only touches these, weighted by count — never the raw stream again. This is why it scales to gigabytes.

The engineering that makes it fast (the real behind-the-scenes)

  • Incremental counts. After a merge, only the neighboring pairs change — so it updates a handful of counts, never recounts everything.
  • A max-heap keyed by pair frequency → grabbing the top pair is O(log n), not a full scan.
  • An occurrence index (pair → where it appears) so applying a merge touches only affected words.

That's why HuggingFace tokenizers is written in Rust: same loop, but these structures train a 50,000-merge tokenizer on gigabytes in minutes.

Using it — split a word it has never seen

Training gave us this ranked list of rules (rank = order learned = frequency):

0w+e→we1l+o→lo2lo+we→lowe3r+_→r_4n+e→ne5w+_→w_6s+t→st7st+_→st_8ne+we→newe9lowe+r_→lower_10lo+w_→low_11lowe+st_→lowest_

Now split slowest — a word that was never in the training corpus — using only those rules.

Step 1 · which pair do we combine? Check every adjacent pair in s l o w e s t _ against the rule list. Three have a rule — so apply the lowest-numbered one (rule #0, which was also the most frequent):

s + lno rule
l + o✓ rule #1
o + wno rule
w + e✓ rule #0
e + sno rule
s + t✓ rule #6

Then repeat — each step, apply the lowest-rank rule that still fits, until none do. The merged token lights up:

"Earliest" and "most frequent" are the same thing

Rule #0 is both the earliest and the most frequent — because training built the rules already sorted by frequency (it always grabbed the most common pair next). So "apply lowest rank first" = "apply most frequent first" — one instruction, two names. Replaying them in that order splits any new word exactly as training would have.

THIS is why the rules are kept

The tokenizer had never seen slowest, yet it split it into s + lowest_. The vocabulary (the list of pieces) couldn't tell it how — only the ordered rules could. Drop them and the tokenizer can't split any new word. The rules are the how-to-split instructions.

3 · Train your own — for real

A 300-token tokenizer that beats GPT-2's 50,257.

Run that same loop on your corpus with the production library — the whole code. I trained one on 6,000 DNA sequences:

from tokenizers import Tokenizer, models, trainers, pre_tokenizers
tok = Tokenizer(models.BPE())
tok.pre_tokenizer = pre_tokenizers.ByteLevel()
trainer = trainers.BpeTrainer(vocab_size=300)   # your target
tok.train(["dna_corpus.txt"], trainer)          # your corpus

It discovered the biology — the tokens it invented include the start codon ATG, stop codon TAG, and motifs:

TGAAAGCCTTATGTCGCACCCTGGCCCAGCGGAATCAGTAG

On unseen DNA, that tiny tokenizer crushes GPT-2 — which has no DNA merges and falls back to near-bytes:

GPT-250,257-token vocab27 tok

Same 48 characters. Yours sees big learned motifs —

The win

A tokenizer 167× smaller is 63% more efficient on its home domain. Fewer tokens = cheaper, longer context, smaller embedding table. Code, protein, and multilingual models all train their own.

4 · Retraining — the catch

You can't hot-swap a tokenizer under a trained model.

Retraining = run the count-merge loop on a new corpus → new merge table. But the tokenizer is joined to the model at the embedding table: token id 9379 → row 9379 of a learned matrix of vectors, and the output head maps back to those ids.

So it drags the model with it

New tokenizer → ids mean different things → the embedding table + output layer no longer line up. You must resize/re-init them and (at least partly) retrain the model. That id → vector coupling is the next session.

5 · Why off-domain text is expensive

No merges apply → it spells out raw bytes.

The merges are shortcuts learned from the training corpus. Match → few tokens. No match → fall back toward one token per byte. The tokens/byte ratio shows it (near 1.0 = raw bytes):

tokenization12 bytes2 tok0.17 tok/byte
भाषा12 bytes6 tok0.50 tok/byte
语言模型12 bytes11 tok0.92 tok/byte
🤖4 bytes3 tok0.75 tok/byte

English gets ~7× compression; Chinese ~none — and each non-Latin character is 3 UTF-8 bytes, so per-byte fallback ≈ 3 tokens per character.

The aha

Training a tokenizer = compress the corpus to word counts, then loop { count adjacent pairs, merge the most frequent, rewrite the words }, and save the ranked merge list. Everything else is just making that loop fast.
